git clone https://github.com/kubernetes-sigs/kubespray.git

pip install --user -r requirements.txt

cp -rfp inventory/sample inventory/mycluster

Редактируем inventory.ini

В блоке [all] указываем список всех хостов.
В блоке [kube_control_plane] список мастеров.
В блоке [etcd] список хостов для etcd, в данном случае он совпадает со списком мастеров.
В блоке [kube_node] указываем список нод и ingress-хостов. У нас ingress сервера по сути являются обычными рабочими нодами, но с помощью настроек мы сделаем так, чтобы на нодах ingress рабочие контейнеры не запускались, а работал только ingress.
В блоке [kube_ingress] указываем список ingress-хостов.
В блоке [k8s_cluster:children] указываем блоки с участниками кластера, а именно мастера и рабочие ноды: kube_control_plane и kube_node.

В inventory/mycluster/group_vars/all/all.yml добавляем:

kubelet_load_modules: true # автоматически загружает модули в ядро системы
kube_read_only_port: 10255 # порт для мониторинга кублетов, для prometeus

В inventory/mycluster/group_vars/all/containerd.yml добавляем:

# Для containerd overlayfs используется по умолчанию, но можно явно указать:
containerd_snapshotter: overlayfs
# Базовые настройки containerd
containerd_storage_dir: /var/lib/containerd
containerd_state_dir: /run/containerd
containerd_max_container_log_line_size: 16384

# Настройка garbage collection для экономии места
containerd_discard_unpacked_layers: true

# OOM Score для containerd (чем меньше значение, тем меньше вероятность быть убитым)
containerd_oom_score: -999

# Настройка зеркал для registry
containerd_registries_mirrors:
  - prefix: docker.io
    mirrors:
      - host: https://mirror.gcr.io
        capabilities: ["pull", "resolve"]
        skip_verify: false
  - prefix: your-private.registry.com
    mirrors:
      - host: https://your-private.registry.com
        capabilities: ["pull", "resolve", "push"]
        skip_verify: false

# Аутентификация для приватных registry (если требуется)
containerd_registry_auths:
  your-private.registry.com:
    username: "your-username"
    password: "your-password"
    # или config: "/path/to/docker/config.json"




В inventory/mycluster/group_vars/all/etcd.yml добавляем:

etcd_memory_limit: 0 # снимаем ограничение 512 мб

В inventory/mycluster/group_vars/k8s-cluster/k8s-cluster.yml добавляем:

kube_network_plugin: cilium
# Рекомендуется для наилучшей производительности Cilium
kube_proxy_remove: true

# Меняем на containerd:
container_manager: containerd

# kube_proxy_mode: iptables
kubeconfig_localhost: true 

В inventory/mycluster/group_vars/k8s-cluster/k8s-net-cilium.yml добавляем:

# Режим работы Cilium: vxlan (туннель) или direct-routing (прямая маршрутизация)
# Для сред, где ноды НЕ находятся в одной L2-сети, лучше использовать vxlan.
# Если ноды в одной L2-сети, можно использовать direct-routing (аналог host-gw у flannel) для большей производительности.
cilium_tunnel_mode: "direct-routing"

# Указываем интерфейс, на котором будет работать Cilium (аналог flannel_interface_regexp)
# Здесь можно указать конкретное имя интерфейса (например, eth0) или регулярное выражение.
# Пример для вашего случая с сетями 10.12.119.0/24 и 10.17.119.0/24:
cilium_interface_regexp: '10\.(17|12)\.119\.\d{1,3}'

# Версия Cilium (опционально, Kubespray установит последнюю стабильную, но можно зафиксировать)
# cilium_version: "v1.15.5"

# Включить Hubble (мощный инструмент observability от Cilium) - НАСТОЯТЕЛЬНО РЕКОМЕНДУЕТСЯ
hubble_enabled: true
hubble_listen_address: "0.0.0.0:4244" # Порт для сбора flow данных
hubble_ui_enabled: true               # Включить веб-интерфейс Hubble
hubble_ui_service_type: NodePort       # Как публиковать Hubble UI
# hubble_ui_service_nodeport: 31234    # Опционально, фиксированный NodePort

Настраиваем ingress.

В inventory/mycluster/group_vars/k8s-cluster/addons.yml добавляем:

ingress_nginx_enabled: true

ingress_nginx_nodeselector:
  node-role.kubernetes.io/ingress: "true" # указываем метку ноды ingress

ingress_nginx_tolerations:
  - key: "node-role.kubernetes.io/ingress"
    operator: "Exists"

ingress_nginx_configmap:
  server-tokens: "False"
  proxy-body-size: "2048M"
  proxy-buffer-size: "16k"
  worker-shutdown-timeout: "180"

Создаём inventory/mycluster/group_vars/kube-ingress.yml и добавляем:

node_labels:
  node.kubernetes.io/ingress: "true" # всем серверам в группе kube-ingress ставить метку
node_taints:
  - "node.kubernetes.io/ingress=:NoSchedule"
Копировать
На ноды в группе kube-ingress ставится ограничение NoSchedule, чтобы на ноды не распределялись поды. Это ограничение могут преодолевать только только те, у кого в tolerations прописана метка ingress. Таким образом, на нодах ingress, кроме самого ingress ничего запускаться не будет.

Приступаем к установке кластера K8S.

ansible-playbook -u root -k -i inventory/mycluster/inventory.ini -b --diff cluster.yml -e kube_network_plugin=cilium


После успешной установки кластера можно проверить, что containerd работает корректно:
# На любой ноде
sudo crictl version
sudo crictl images
sudo crictl pods

Отлично! После того как Kubespray завершит установку кластера, файл kubeconfig для подключения будет автоматически создан и сохранён на той машине, откуда вы запускали ansible-playbook (вашей рабочей станции или jump-хосте).

Где Kubespray сохраняет kubeconfig
По умолчанию Kubespray создаёт копию конфигурационного файла в двух местах:

Локальная копия для администратора (самый удобный способ): В директории artifacts внутри вашего инвентаря. Это контролируется переменной kubeconfig_localhost: true, которую вы уже установили ранее в файле inventory/mycluster/group_vars/k8s-cluster/k8s-cluster.yml .

На мастер-нодах: Файл также находится на первой мастер-ноде кластера по пути /etc/kubernetes/admin.conf.

Инструкция по настройке доступа
Шаг 1: Скопируйте kubeconfig с машины, где запускался Kubespray
После успешного завершения плейбука, выполните на своей локальной машине (откуда вы планируете запускать kubectl) следующие команды. Вам нужно скопировать файл с сервера, где лежит ваш Kubespray проект.

bash
# Создайте директорию .kube, если её нет
mkdir -p $HOME/.kube

# Скопируйте конфиг из директории artifacts вашего инвентаря
# (предполагается, что вы находитесь в корне директории kubespray)
cp inventory/mycluster/artifacts/admin.conf $HOME/.kube/config
Если вы запускали Kubespray с удалённой машины, сначала скопируйте файл оттуда с помощью scp:

bash
scp user@<ip_вашего_сервера_с_kubespray>:~/kubespray/inventory/mycluster/artifacts/admin.conf ~/.kube/config
Шаг 2: Настройте правильный IP-адрес сервера API
Файл admin.conf по умолчанию содержит внутренний IP-адрес или DNS-имя первой мастер-ноды. Чтобы подключаться к кластеру извне (например, из Яндекс.Облака или вашей локальной сети), вам может понадобиться заменить этот адрес на публичный IP мастер-ноды или адрес балансировщика.

Проверьте текущий адрес сервера в конфиге:

bash
kubectl config view --minify -o jsonpath='{.clusters[0].cluster.server}'
Если вы видите там https://192.168.x.x:6443 (внутренний IP), его нужно изменить. Узнайте публичный IP-адрес вашей мастер-ноды в консоли Яндекс.Облака. Затем выполните:

bash
# Замените <публичный-IP-мастера> на реальный IP-адрес
kubectl config set-cluster kubernetes --server=https://<публичный-IP-мастера>:6443
Если вы настраивали высокую доступность с использованием балансировщика или kube-vip , используйте его IP-адрес.

Шаг 3: Проверьте подключение
Теперь можно проверить работоспособность кластера:

bash
# Посмотреть информацию о кластере
kubectl cluster-info

# Посмотреть список узлов (должны отобразиться все ваши master и worker ноды)
kubectl get nodes

# Посмотреть все поды во всех неймспейсах
kubectl get pods --all-namespaces
Вы должны увидеть список нод со статусом Ready и все системные поды в статусе Running.
